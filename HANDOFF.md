## 0. TL;DR

We're rebuilding the SBC Guest Management app — a 3-user-group portal (Impact Cell, Follow Up Officer, Follow Up Team) for tracking "guests" through outreach → follow-up → integration — on a fresh **Laravel 12 + Inertia + React 18 + Breeze + Spatie Permission/Activitylog** stack. The MySQL 8.4 DB (`impact_guest` on localhost, user `ipcDBurs22`) is bootstrapped and live. **Phases 02 → 06 are green (58 / 15 / 36 / 22 / 14 sub-assertions all passing — see §1 for per-phase detail). Phase 05c follow-ups (guest edit form + controller `AuthorizesRequests` trait fix + source-of-truth Edit page + DROPPED-FROM-DRY refactor) also shipped. Phase 06 adds the Team Dashboard with 4 team KPIs, inline follow_up_status editing, Contact Sections timeline, and View-Only mode for Follow_UP_View_Only. **Auth UI polish prelude is now shipped** — split-screen brand panel (indigo gradient + animated glow orbs + SVG grid pattern + Heroicons feature pills), show/hide password with `type="button"` (Enter-key safe), envelope/lock icon prefixes, `kbd ↵` keyboard hint, polished CTA, and `/public/logos/{logo,logo1}.png` asset hosting. **`Phase 06b → 06c — UI Polish`** (Tokens → Chrome → Pages) is **scoped and ready** — full plan in `Implementation/Phase_06b-06c_UI_Polish.md`. Next up: **Phase 06b (Foundations + Chrome)** then Phase 06c (Pages + Tables), then Phase 07 (Impact Cell Leader forms).

## 4. The 9 roles + 3 groups (glossary)

The **9 Spatie roles** are seeded by `RolesAndPermissionsSeeder`:

```
Administrator       Supervisor         FollowUpOfficer
Follow_UP           Follow_UP_Admin    Follow_UP_View_Only
Impact_Leaders      Impact_Cell_Admin  Impact_Cell_Report
```

They collapse into **3 functional groups** (defined in `RoleHelper::GROUP_*` constants):

| Group key         | Members                                                     | Owns these Guest columns                                                                                                                                                                            |
| ----------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `impactCell`      | `Impact_Leaders`, `Impact_Cell_Admin`, `Impact_Cell_Report` | `impact_status`, `nearest_impact_cell_id`                                                                                                                                                           |
| `followUpOfficer` | `FollowUpOfficer`, `Follow_UP_Admin`                        | `gender`, `marital_status`, `age`, `phone`, `address`, `contacted_status`, `join_when`, `days_available`, `comments`, `visited`, `visited_at`, `indicated_to_join`, `visitation_status`, `feedback` |
| `followUpTeam`    | `Follow_UP`, `Follow_UP_View_Only`                          | `follow_up_status`, `follow_up_contacts`                                                                                                                                                            |
| (no group)        | `Administrator`, `Supervisor`                               | `Administrator` writes everything; `Supervisor` writes nothing on Guest                                                                                                                             |

**Note (post-Phase-05 fix):** all matrix KEY names are **snake_case** to match the production HTTP wire format (`$request->all()` returns snake_case, DB columns are snake_case, GuestResource outputs snake_case, frontend types are snake_case). An earlier v1 of this file had camelCase keys and was silently stripping every multi-word field from FollowUpOfficer writes — fixed in the post-Phase-05 commit. A regression guard in `verify_phase02_run.php` / `verify_phase04_run.php` fails fast if a future contributor types camelCase.

Source of truth: `app/Support/RoleHelper.php` (GROUP_GUEST_OWNER matrix) + `Implementation/03_Three_User_Groups.md` (design intent).

## 9. Common gotchas (quickref)

The full list is in `Implementation/00_Laravel_Bridge.md` § 7. The three that bit us during Phase 02:

1. **Windows/Laragon — `composer require` dies with `Access is denied (code: 5)` on `bootstrap\cache\services.php`.**
   Root cause: **Laragon's Watch file-monitor service** in the tray menu scanning `bootstrap/cache/` mid-rename. Toggle Watch OFF in the tray, re-run, then re-enable. Manual fallback: `rm -f bootstrap/cache/*.tmp bootstrap/cache/services.php bootstrap/cache/packages.php` + re-run with `--no-scripts`.

2. **Spatie migrations are `.stub` files — NOT auto-discovered by Laravel 12.** `php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"` returns "No publishable resources" in Spatie v8.x. You must `cp` the stub files into `database/migrations/` manually with a timestamp prefix (see Phase 02 § 6 above for the exact paths).

3. **`User::activeRole()` cache staleness** — if an admin strips a Spatie role without calling `forgetCachedPermissions()`, the accessor falls back to the first Spatie role (correct behavior, but the stale-column value is silently ignored). Mitigation: `RolesAndPermissionsSeeder::run()` calls `forgetCachedPermissions()` before AND after seeding.
4. **Cross-platform paths / `Storage::disk('public')`.** All file storage MUST go through Laravel's `Storage` facade (`Storage::disk('public')`). Hardcoded `C:\\…` paths will break on the Linux deploy. Per bridge §7 pitfall #3.

5. **Stale Vite from another project (especially `Echo_GPT` in `application_folder/`) hijacks port 5173 — symptoms: blank page even though `curl /login` returns HTTP 200 + HTML.**
   If you're staring at a **totally blank browser page** even though `curl http://impact_portal_plus.test/login` returns **HTTP 200 + ~24 KB of HTML with valid Inertia `<div id="app" data-page="...">`**, the cause is almost always a _different_ `vite` process that has bound port 5173 before yours did. In our confirmed incident during Phase 05, PID 1844 listening on port 5173 was `node "C:\\Users\\Delluser\\Documents\\application_folder\\Echo_GPT\\apps\\desktop\\node_modules\\.bin\..\\vite\\bin\\vite.js"` — a stale Vite from a completely unrelated Electron desktop project. Every `<script type="module" src="http://localhost:5173/resources/js/app.tsx">` request from our HTML got answered with Echo GPT's `index.html`. The browser tried to execute HTML as ESM, threw a `SyntaxError` at hydration, and the React tree never mounted — but the network panel shows HTTP 200 so it looks like the server is fine. **The page is blank because hydration crashed silently, NOT because Laravel is broken.**
   Vite's own transforms **were** working (`/@vite/client`, `/@react-refresh` returned correct JS). Just the page-level assets were stolen.

    ## Diagnose (one PowerShell + one netstat; both run from `C:\laragon\www\impact_portal_plus`)

    ```bash
    netstat -ano | grep ':5173.*LISTENING'
    #  ↓
    # TCP    0.0.0.0:5173    0.0.0.0:0    LISTENING    <PID>

    # Then in the SAME Git-Bash:
    powershell -NoProfile -Command "(Get-CimInstance Win32_Process -Filter 'ProcessId=<PID>').CommandLine"
    #  ↓
    #  If the CommandLine ends in ...\application_folder\Echo_GPT\...\vite\bin\vite.js
    #  instead of  ...\impact_portal_plus\node_modules\vite\bin\vite.js
    #  → you've been hijacked.
    ```

    The port-holder's identity is the smoking gun — yours should always be a node running from `impact_portal_plus\node_modules\.bin\..\vite\bin\vite.js` (NOT from `Echo_GPT` or any other project on this PC).

    ## Fix (3 commands, no `pnpm dev` wrapper)

    ```bash
    # 1. Kill every node process whose CommandLine mentions the wrong vite.js (single taskkill does not stick — see note below)
    powershell -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { \$_.Name -eq 'node.exe' -and \$_.CommandLine -match 'vite' } | ForEach-Object { \$_ | Invoke-CimMethod -MethodName Terminate }"
    sleep 2
    # 2. Start YOUR project's vite DIRECTLY (no pnpm middleware, no Vagrant middleman, --strictPort fail-fast)
    nohup node node_modules/vite/bin/vite.js --port 5173 --strictPort --host 127.0.0.1 > vite.log 2>&1 &
    ```

    ## Verify

    ```bash
    curl -is http://localhost:5173/resources/js/app.tsx --max-time 8 | head -5
    # ↓
    # HTTP/1.1 200 OK
    # Content-Type: text/javascript                ← that's the signal
    ```

    ## Why a single `taskkill /F /PID <n>` is NOT enough

    On this PC we observed PID 1844 returning to port 5173 with the Echo_GPT command line after one `taskkill /F /PID` cycle. The PowerShell CIM `Terminate` sweep over **every** `node.exe` whose `CommandLine` matches `vite` is the only reliable kill — `taskkill` on a single PID is racy when the offending vite's lifeline isn't yours.

    ## Future prevention
    - Don't run `pnpm dev` / `npm run dev` from inside other projects in the same Laragon stack while developing here — they will compete for 5173.
    - `--strictPort` (the flag above) makes your vite fail-fast rather than silently fall back to 5174 if 5173 is taken.
    - The echo'd process identity from `netstat`'s PID slot is the FIRST thing to check whenever the dev server "works in `curl` but is blank in the browser". Six-second debug, saved a blank-page panic in Phase 05.
